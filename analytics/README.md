# LAE Sales Analytics

This application opens from the Farming Hub home screen at `/lae-analytics/`. It has its own Node process, static assets, SQLite database and deployment. Purchase, RO costing and price-list databases are not mounted or opened here.

## Release boundary — both computers

- Purchase/costing deploys `main` using the root `Dockerfile`.
- Analytics deploys `lae-analytics-live` using `/analytics/Dockerfile`.
- Use a separate checkout for each flow. Before editing, fetch origin, confirm the branch and preserve other local changes. Push normally; never force-push over work from the other computer.
- Analytics changes stay inside `analytics/` on `lae-analytics-live`. Do not merge the whole analytics branch into purchase or deploy the purchase application for an analytics-only change. Cherry-pick a deliberately reviewed shared integration change if required.
- The analytics container copies only `analytics/`; it has no dependency on the current purchase source tree. Its persistent volume mounts `/app/analytics-data`, with `analytics.sqlite` and immutable imported source revisions. Do not mount `/app/data` or copy a purchase database into it.
- Run `node --test analytics/tests/*.test.mjs`, syntax checks and a focused browser check for affected behavior. Verify the analytics health SHA and MASTER control totals after a release. Routine analytics releases do not require repeated purchase recovery ZIPs or a full purchase regression cycle. This exception applies only to this module.

Shared infrastructure remains: the host, reverse proxy and Farming Hub authentication. Analytics asks `/api/session` for the current account on every API call; no purchase data is returned by that identity endpoint. Existing LAE access is required to read; administrator access, same-origin and CSRF checks protect imports. An unavailable sign-in service fails closed. A host or identity outage can still affect both applications.

## Data contract

The initial source is MASTER in the approved workbook. Reported stock uses column CD and pipeline uses BU, retaining source discrepancies as exceptions. Warehouse columns Z, AD, AM, AR and AI map to B2C–TN, B2B–TN, B2B–AP/TS, B2B–Karnal and shared Chennai. Chennai is included once in the all-centre MASTER total and shown separately for a selected centre. Pipeline is shared and unallocated. Monthly pipeline is grouped from the source brand inputs; brand codes are omitted from reporting.

Reports drill Product category → Engine/blade specification → Grade → Item code/model. For chaff cutters, the MASTER engine field holds the blade specification. Main segment mapping remains pending. Stock cutoff is unknown; changing pipeline month does not redate stock. Month years are inferred from the stock source filename and sequence, and are labelled accordingly. The purchasing extension below adds item-level allocations from a separate immutable forecast import; shortages remain item-code-wise.

Data is imported through authenticated `POST /lae-analytics/api/lae-analytics/import` with `{dataset, expectedId}`. `expectedId` must match the active source (null initially). Imports validate controls and remain immutable; identical imports replay safely. Keep workbook data, credentials and SQLite files out of Git and static assets. A new import does not replace or modify purchase/costing records.

Health: `/lae-analytics/api/health`. Local server: `node analytics/server.mjs`. Production identity origin is fixed to `https://purchase.dvjassociates.com`.

## Monthly sales and annual business plan

Sales use fiscal April–March periods from the two-year workbook. Read only detail rows; fiscal, state, category and grand totals are reconciliation controls, never additional sales. The separately appended Farming Hub block belongs to B2C–TN and is included once. Blank item cells inside supplied cost-centre months mean no recorded sales; absent cost-centre periods remain unavailable. Preserve the workbook's original SKU, category, row and values in every immutable import. Sales quantity is reported quantity; value and returns treatment are not supplied.

Known brand prefixes GJ, KD, TT, SG, ST and TX are removed for reporting. Exact resulting item codes inherit MASTER category, engine/blade and grade; no fuzzy model matching or engine/grade inference. Unmatched items remain visible in their source category, with unmapped specification/grade. Missing/unknown item codes retain separate source-row identities. Classification is pinned to the MASTER import used at sales import time; a changed MASTER source is flagged rather than silently rewriting sales.

October 2026 is partial through 14 October, confirmed by the user. Completed-month comparisons exclude partial months and use only cost centres with coverage in both years. Prior B2C–TN is absent. FY2025–26 TN contains only Battery Sprayer Spares; completeness is pending a deferred user clarification, so TN is excluded from year-on-year calculations while its supplied sales remain visible. Do not replace missing history with zero or annualize partial October.

The user-supplied FY2026–27 ABP covers B2B–AP/TS and B2B–TN at product-category level. Preserve the blank AP/TS Mini Weeder target as unspecified. Achievement uses year-to-date sales through the source cutoff in only categories/cost centres with a stated target, regardless of the selected monthly view. Show excluded sales separately. No ABP is allocated to engine, blade, grade or SKU. Remaining category targets sum nonnegative shortfalls by category and cost centre; overachievement elsewhere does not offset a shortfall. This is not a purchase-quantity calculation.

Sales and ABP import together through authenticated `POST /lae-analytics/api/lae-sales/import` with `{dataset, stockId, expectedId}`. Validate all source-row totals, every cost-centre/month control and ABP totals. The active sales token and pinned MASTER ID reject concurrent/stale replacement. Append-only sales tables share only the analytics database; stock imports remain unchanged. Reports use bounded monthly arrays, indexed in-memory groups and 50-row pages; no per-group rescan of the full source. Limits are 32 MB, 50,000 detail rows, ten financial years and forty cost-centre coverage controls. The initial 883 rows and 10x 8,830 fit the count bound; 100x 88,300 is rejected and requires a new storage/import design, not a silent truncation. This is a bounded design assessment, not a load-test claim.

## Purchasing extension to DEC-138 — 14 October 2026

Confirmed scope: finish a FY purchasing guide using category ABP, forecast SKU mix, MASTER stock and pipeline, with unresolved decisions retained for later review. Keep the existing sales history unchanged. The separate purchasing reports add B2C and North planning bases; the original sales-history ABP cards remain approved B2B targets only.

- B2C–TN: provisional category monthly average = completed April–September sales / 6. FY equivalent = average x 12, excluding partial October from the average. Remaining demand = nonnegative annual equivalent less FY actuals.
- North: raw October–March forecast is the closeout target, with no demand extrapolation. Its comparable FY equivalent adds completed April–September actuals. Deduct October sales from October forecast at each item code, flooring at zero; overachievement on one item cannot offset another. Blank future SKU plans stay blank. North is fixed in demand stress scenarios.
- B2B AP/TS and TN: retain supplied category ABP. Missing targets stay unknown; unplanned sales remain visible.
- Monthly phasing is an explicit provisional assumption: spread remaining category quantity over the remaining FY with equal full-month weights (October remainder 17 days, other months 31 weight units). This is not a seasonal forecast. Positive SKU quantities in each category/centre/month determine the SKU shares. Whole-unit largest-remainder allocation uses exact BigInt products and remainders with source order as deterministic tie-breaker. Category/months lacking positive SKU forecasts retain unallocated demand; do not redistribute it into other months or models.
- Forecast import uses the four centre-specific MASTER blocks, row 3 month labels and row 4 totals. Retain cached MASTER totals over discrepant brand sums. All-blank brand inputs plus a cached zero are missing, not a confirmed zero. Explicit zeros remain known. Year is inferred from the filename and is flagged because older template labels persist.
- Consolidated purchase quantities pool stock at the same item code across centres, including Chennai once; transfers are an assumption, not an allocation or booking. A scenario excludes North stock. Stock cutoff is unknown, so the projection does not deduct sales again. No new allocation of shared stock/pipeline to individual cost centres is invented.
- Annual net requirement is max(0, allocated remaining demand - usable MASTER stock - pipeline within the FY), calculated separately by item. Monthly receipt gaps use a running balance with source-month arrivals assumed before demand. Later arrivals cannot erase an earlier timing gap. Monthly gaps may exceed annual net requirements; expose that difference as timing / expedition risk, not an instruction to duplicate purchases. Future demand blanks remain visible and keep total requirements incomplete.
- Scenario inputs: remaining demand 80/100/120 percent, pipeline as labelled or one month late, all stock or excluding North, illustrative total lead time 30/60/90/120 days. Order-by dates are need-by minus selected lead time; need-by is 15 October for the partial month and first of each later month. No supplier availability, MOQ, safety buffer, margin, landed cost, seasonal model or budget is inferred. Sensitivity recomputes the exact allocation engine, not a rescaling of rounded item outputs.

Read-only screens: consolidated purchasing overview, category → engine/blade → grade → item requirements, monthly receipts, category/centre ABP and allocation coverage, issue register, sales history and MASTER stock. A filtered CSV fair worksheet includes supplier, quote, MOQ, pack, confirmed lead-time and purchase-note columns for follow-up. CSV cells neutralize spreadsheet formula prefixes. Higher-level main segments are unassigned pending an approved mapping; engine/blade/grade reporting is available. Do not automatically treat inferred quantity priorities as spend or profit rankings.

Forecast import: `POST /lae-analytics/api/lae-planning/import` with `{dataset, stockId, salesId, expectedId}`. Administrator + Origin + CSRF required. Validate all 24 centre/month controls, code/row identity, full source coverage and discrepancy register. Immutable imports pin both active source IDs. Changed sales or stock makes the plan unavailable until reconciled, rather than silently restating it. GET `/api/lae-planning/workspace` preserves scoped access. It never reads or changes purchase/costing records.

Scale: 6,432 forecast records initially; 10x 64,320 fits the 250,000 row and 32 MB import bounds if serialized size also fits. 100x 643,200 is rejected. Cache at most four source/scenario projections; category/month indexes avoid full-source scans per item. Item tables page at 50, export covers the full filter. Current source validation and browser timings are not load certification. Larger imports require a row-based store and paged issue endpoints before increasing limits.

Validation: dedicated tests cover exact rounding, time-vs-net gaps, same-item netting, B2C averages, North scope, missing-vs-zero, immutable imports, permissions, stale source rejection and prior stock/sales behavior. An independent Python Fraction implementation verifies every mapped item/month and all final controls against source data. Focused desktop/mobile browser checks cover drills, scenario controls, flags and CSV. UI-01/02/05/06/12 and HIG R021/R024/R100/R135 apply; semantic tables remain horizontally scrollable within named regions, 44px controls and no new animation dependency. This extension stays within the analytics branch/process; no purchase build or database migration occurs. Publication is verified separately through exact release SHA, served files, source IDs and authenticated readback.
